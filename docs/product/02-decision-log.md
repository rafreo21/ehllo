| DEC-033 | 2026-08-03 | Add `phone`/`phone_verified`/`phone_verified_at` to `public.users` as internal account fields, distinct from the public Card's own optional phone method. Collect them via a new "Edit profile" screen in My Account, not during card creation or onboarding. Full phone-OTP verification is schema-ready (`update_my_account_profile` resets `phone_verified` whenever the number changes) but not wired to a live SMS provider yet — no provider is chosen. Email is treated as already verified for security purposes, since every sign-in requires completing a fresh 6-digit email OTP; `get_my_app_context()` now also surfaces `email_verified` (from `auth.users.email_confirmed_at`) for display. | The public Card is a shareable identity a user may deliberately keep partial or pseudonymous; the internal account record needs real contact details for account-recovery and anti-takeover purposes, so the two must not be the same field. | Accepted | Revisit once an SMS/OTP provider (e.g. Twilio, Supabase phone auth) is selected — implement the actual send/confirm flow against the already-reserved `phone_verified` field. |
| DEC-032 | 2026-08-03 | Auto-create a default draft Card the first time a user's personal workspace is provisioned (inside `provision_personal_workspace`, gated on `v_workspace_created` so it only ever fires once per user). | DEC-031 | 2026-08-03 | Add optimistic-concurrency conflict protection to Encounters, Cards, Contacts, and Events. Mobile and consumer-web review/edit paths send the last server revision; conditional database updates reject stale writes atomically. Event conflicts return the latest version before any guest-notification email is queued. The capture wizard's in-progress autosave remains deliberately revision-free while one device owns that draft. | These records contain the identity, private context, schedule, and follow-through data most likely to be open on two devices. A stale client must reload rather than silently replace newer trusted data or notify guests about an obsolete schedule. | Accepted | Extend the same pattern when another user-editable shared object gains multi-device editing. |
